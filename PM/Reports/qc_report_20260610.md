# QC 검증 결과 보고서 (2026-06-10)

## 1. 개요 및 검증 목적
* **작성자**: QC 에이전트
* **검증 대상**: 1일차부터 현재(4일차)까지 개발된 키오스크 관리 시스템(Backend 및 Partnercenter Frontend) 전체 기능
* **검증 목적**: 기획 및 사용자 의도대로 비즈니스 로직이 구현되었는지 확인하고, E2E 통합 테스트를 통해 시스템 연동 정합성 및 안전성을 확인하며, 결함 발견 시 실시간 조치.

---

## 2. 주요 기능 및 구현 현황 검토
1일차부터 개발된 핵심 시나리오별 구현 타당성은 다음과 같습니다:

1. **회원 가입 및 권한 체계**
   * 점주 가입 시 기본 권한 `NONE`, 상태 `PENDING` 설정.
   * 개발자/본사 관리자(`DEV`, `HEAD`)에 의한 사업자 승인 처리 기능 작동.
   * **[의도 반영 확인]** 사업자 승인 완료 시 점주의 권한이 `MANAGER`로 자동 상승하고 상태가 `ACTIVE`로 변경됨으로써 후속 매장 및 기기 등록 권한이 활성화됨.

2. **사업자 정보 및 매장 매핑**
   * 점주의 사업자 정보 등록 시 가맹 매장(`Store`) 자동 가상 생성 처리 확인.
   * `stores` 테이블의 `owner_name` 컬럼과 점주 정보 동기화 검증.

3. **키오스크 기기 관리 및 다중 권한 (KioskAdmin)**
   * 기기 등록 시 난수 기반 고유 기기 코드(`KS` 시작) 생성 확인.
   * 점주가 기기를 등록하면 해당 점주가 `MASTER` 권한으로 `kiosk_admins` 관계에 매핑됨.
   * 점주가 직원(`STAFF`) 또는 타 점주를 해당 기기의 부관리자로 지정하고, 권한 수정 및 해제하는 다중 관리자 권한 매핑 기능 확인.

4. **카탈로그 빌드 및 클라이언트 동기화**
   * 매대(Shelve) 생성 -> 카테고리 생성 -> 상품(Product) 생성 및 특정 키오스크 귀속 로직 확인.
   * 키오스크 클라이언트가 동기화 API 호출 시 귀속된 카테고리/상품 정보만 정밀 필터링하여 응답하는 연동 정합성 검증.

5. **가상 결제 및 실시간 재고 차감**
   * 키오스크 클라이언트에서 가상 결제 요청(`POST /kiosk_client/pay/mock`) 시 주문 정보 적재 및 상품 재고 실시간 차감 처리 확인.

6. **글로벌 기기 격리 필터 (X-Kiosk-Id)**
   * 요청 헤더의 `X-Kiosk-Id`를 기준으로 대시보드 매출 통계 및 주문 리스트 조회 시 해당 기기 귀속 데이터만 정확하게 분리 필터링하는 멀티 테넌시 격리 로직 확인.

## 3. 테스트 중 발견된 문제 및 수정 사항 (Hotfix)

검증 테스트 진행 중 백엔드 API에서 발견된 **2건의 결함**을 현장에서 즉시 수정 조치 완료하였습니다.

### 결함 1: `NameError: name 'UserStatus' is not defined`
* **현상**: DEV 관리자가 사업자 등록증 승인 API(`PATCH /users/{user_id}/verify-business`) 호출 시 `500 Internal Server Error` 발생.
* **원인**: `Backend/routers/user.py`에서 승인 상태 변경 시 `UserStatus.ACTIVE`를 사용하고 있었으나, 파일 상단 임포트문에 `UserStatus`가 누락됨.
* **조치**: `routers/user.py` 상단에 `from models.user import UserInfo, UserRole, UserStatus`로 임포트 구문을 수정하여 결함 해결.

### 결함 2: `DetachedInstanceError` (Lazy Loading/Expunge 오류)
* **현상**: 매출 및 주문 리스트 조회 API(`GET /order/`) 호출 시 Pydantic 직렬화 과정에서 `DetachedInstanceError` 발생하며 `500 Internal Server Error` 리턴.
* **원인**: `Backend/routers/order.py`에서 DB 세션 오염을 방지하기 위해 `db.expunge(order)`를 호출하여 인스턴스를 세션에서 분리시켰으나, Pydantic이 관계형 속성(`items`)을 직렬화하기 위해 접근하려 할 때 지연 로딩(Lazy Loading)이 불가하여 발생.
* **조치**: 
  * 주문 리스트 API(`get_orders`)에서는 `expunge`를 사용하지 않고, Pydantic Schema 객체로 먼저 변환한 뒤 마스킹 처리(`OrderResponse.model_validate(order)`)를 수행함으로써 DB 오염 방지와 지연 로딩 문제를 안전하게 해결.
  * 기타 상세조회, 취소, 환불 API에서도 불필요하고 에러를 유발하는 `db.expunge` 호출을 완전히 제거하여 API의 안정성을 회복.
